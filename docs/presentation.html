What it is

A shared engine, run separately for every business you serve.

Most teams that offer WhatsApp messaging to multiple client businesses end up building the same thing three times: credential storage, webhook routing, and campaign tooling — once per client, because nothing was built to share. notify-sdk is that shared layer, built once and hardened for every tenant that runs on it, reachable through an internal admin console for your operators and a REST API for your — or your clients' — developers.

Their own number, their own brand

Every tenant messages customers from their own WhatsApp Business number, with their logo and colors reflected back in their own dashboard.

For developers

How it works

From onboarding to an answered customer, in six stages.

Every message — a single reply or a campaign to twenty thousand contacts — moves through the same six-stage path. Nothing about stage four changes when a new tenant is added in stage one.

01 / ADMIN

Admin onboards

Ops creates a tenant — name, logo, brand color, WhatsApp Business credentials.

02 / ONBOARDING

Credentials verified & sealed

Checked live against Meta's Graph API, then encrypted with a per-tenant key before storage.

03 / API

Integration

Their developers integrate against /v1/send with a scoped API key — or ops sends straight from the dashboard.

04 / MESSAGING

Message sent

Text, media, or an approved template — from that tenant's own number, one-off or as a campaign.

05 / INTERACTION

Customer replies

One webhook resolves the right tenant, checks its signature, routes the reply, and handles STOP/START.

06 / ANALYTICS

Numbers update live

Sent, delivered, read, failed, and replies roll up per tenant and per campaign — recomputed on every refresh.

Multi-tenant architecture

One process. One database. Zero cross-tenant paths.

A tenant's identity is decided once, when its client is constructed — never passed around later as a parameter that a bug could drop or swap. Every tenant's rows in the shared database are scoped by tenant_id at the query level, and every tenant's decrypted credentials live only inside its own in-memory client instance.

AI & automation

A first response that never oversteps, and an assistant that never sends without asking.

Automation on top of a customer-messaging platform has an unusually high cost of getting it wrong — so every piece here is capped, attributed, or gated by design, not left to run unsupervised.

AI-assisted first response

A tenant's own OpenAI or Anthropic key answers routine replies, capped per conversation, and hands off to a human — deterministically, not silently — the moment it can't help or hits that cap. It never sends to a contact who's opted out.

Outbound event webhooks

Send, delivery, read, and reply events pushed to a tenant's own CRM or helpdesk, HMAC-signed and SSRF-guarded, with an endpoint automatically disabled after 10 consecutive failures rather than retried forever.

A shared inbox, tagged and assignable

One merged thread per customer — sends and replies together — with assignment, status, and searchable tags on every contact, so support agents stop reconstructing history from raw logs.

An MCP server for Claude, Cursor, and friends

Any MCP client reads a tenant's logs through the exact same API key and guardrails as every other caller. Write access is opt-in and off by default; bulk send is never exposed to it at all.

Security & data isolation

Built to survive a bad actor, a bad deploy, and a bad admin.

Security in a multi-tenant system isn't one feature — it's a property that has to hold at every layer: storage, transport, and process boundaries. Here's what holds it up.

01

Per-tenant encryption keys

Every tenant's WhatsApp credentials are encrypted with AES-256-GCM using a key derived via HKDF from a single root key — no tenant shares another's key material.

02

Rotatable root key

The root key itself can be rotated without downtime; each credential tracks the key version it was sealed with, so rotation is a background migration, not a cutover.

03

Fail-closed webhooks

Every inbound webhook's HMAC-SHA256 signature is verified against the receiving tenant's own app secret. Missing or invalid — the payload is rejected, not silently accepted.

04

Tenant-scoped storage

Every query against messages, contacts, campaigns, and preferences is scoped to a tenant_id — there is no query shape that spans tenants by accident.

05

Salted, hashed credentials

Admin passwords and API keys are hashed with scrypt before storage — never compared or logged in plaintext.

06

A full audit trail

Every credential rotation, branding change, and API key issuance is recorded against the admin who made it, with a timestamp.

Why not just call Meta's API directly

The Cloud API gives you a wire. It doesn't give you a platform.

WhatsApp's Cloud API is a capable, low-level primitive — but it has no concept of "tenant." Every team that wants to serve more than one client business ends up rebuilding the same layer around it. notify-sdk is that layer, already built.
