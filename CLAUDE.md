# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A multi-tenant WhatsApp Business Platform SaaS. `packages/notify` is a WhatsApp Cloud API SDK; the rest of the monorepo turns it into a platform where an internal ops team (`apps/admin`) onboards client businesses, each with fully isolated credentials, branding, contacts, templates, and message history, and exposes a tenant-facing REST API (`apps/api`'s `/v1/*` routes) for those businesses' own backends to send messages. See `README.md` for the full scenario/use-case list and `packages/notify/README.md` for the SDK's API reference.

pnpm workspace + Turborepo monorepo: `packages/notify` (SDK), `apps/admin` (Next.js ops panel), `apps/api` (Express — single-tenant demo + multi-tenant API), `apps/web` (Next.js — untouched single-tenant SDK usage reference), `packages/mcp-server` (MCP server exposing a tenant's `/v1` API to Claude/Cursor/etc — a pure new consumer, touches nothing else).

## Real-world use cases and where they live

- **OTP/verification codes, task assignments, approvals, deploy alerts, generic alerts with buttons** — session messages (within Meta's 24h customer-service window) built by `TemplateEngine`'s built-in registry (`packages/notify/src/core/TemplateEngine.ts`) or a custom `notify.registerTemplate(name, builder)`. Sent via `NotifyClient.send()`.
- **Order shipped/marketing broadcasts to a whole audience, reachable even outside the 24h window** — real Meta-approved (HSM) templates. A tenant's approved list is pulled via `NotifyClient.syncTemplates()` (needs `wabaId`) and stored in `wa_templates`; a send passes `SendOptions.hsmTemplate` instead of `template`. `apps/admin`'s Templates tab (sync) and Campaigns page (parameterized send against a persisted `broadcast_list`) are the UI for this end-to-end flow.
- **Invoices, receipts, product photos, voice notes** — `SendOptions.attachment` (`image`/`video`/`document`/`audio`, a public HTTPS `link` — Meta fetches it, no pre-upload needed). `apps/admin`'s per-tenant media library (`media_assets` table, Vercel Blob-backed) is where these links come from in practice.
- **Customer replies, button taps (Approve/Reject, Mark done, etc.), STOP/START consent management** — inbound webhooks. Single-tenant: `WebhookHandler`. Multi-tenant (the real path): `TenantWebhookRouter` resolves the tenant from the payload's `phone_number_id`, verifies against that tenant's own `appSecret`, then dispatches — see the "tenant identity is bound at adapter-construction time" note below for why there's no `tenantId` parameter anywhere in this call chain. Every reply is persisted to `message_replies` (not just event-emitted) so it's queryable later.
- **Onboarding a new client business end-to-end** — `apps/admin`: create tenant → upload logo/set brand color → enter WhatsApp credentials (live-verified against Meta's Graph API before the save is even allowed to persist) → sync templates → send a real test message, all without touching code or redeploying anything.
- **A client's own backend sending messages programmatically without ever seeing Meta credentials** — `apps/api`'s `/v1/send` etc., authenticated by an API key ops issued them in `apps/admin`'s API Keys tab. This is the integration point for literally any external system, not just Node.
- **"Why did tenant X's credentials change last week?"** — `admin_audit_log`, written on every credential/branding/API-key mutation in `apps/admin`, attributed to the acting admin user.
- **"How many people did we actually reach, and did anyone respond?"** — the Analytics tab (`apps/admin`'s default tab on a tenant page): live sent/delivered/read/failed/reply rollups and per-campaign performance, computed on every request from `notify_log`/`message_replies`, never a cached snapshot. See `lib/analytics.ts`.
- **A first-line auto-reply to inbound messages, with a human handoff when the bot can't help** — per-tenant BYO OpenAI/Anthropic config (`ai_configs`, `apps/admin`'s AI Assistant tab), dispatched from `apps/api/src/lib/aiAutoReply.ts` on every inbound `'reply'` event. Capped per-conversation (`claim_ai_reply_slot`, atomic), single-turn (no conversation history yet), and never bypasses `GuardEngine`'s opt-in check just because the reply is AI-generated. On cap/failure it hands off deterministically (`ai_autoreply_disabled` + `ai_handoff_summary`) rather than looping.
- **Pushing send/delivery/reply events into a tenant's own systems (CRM, support desk, data warehouse)** — per-tenant outbound webhook endpoints (`webhook_endpoints`, `apps/admin`'s Webhooks tab), HMAC-signed, SSRF-guarded (`packages/notify/src/security/SsrfGuard.ts`), auto-disabled after 10 consecutive failures.
- **A shared inbox for support agents to see and reply to customer conversations** — `conversations` (one row per `(tenant_id, contact_phone)`), `apps/admin`'s Inbox page: merged `notify_log` + `message_replies` thread view, assignment, status, and a composer that reuses the same `client.send()` path as Test Send.
- **Segmenting contacts for targeted campaigns ("VIP", "trial-expiring", etc.)** — `contacts.tags` (`TEXT[]`, GIN-indexed), tag-merge-on-CSV-import vs. explicit-replace-on-edit, filterable in `apps/admin`'s Contacts page.
- **Letting an AI assistant (Claude Desktop, Cursor, etc.) read logs or send messages on a tenant's behalf** — `packages/mcp-server`, a thin MCP server over the tenant's own `/v1` API (same API key, same guardrails). Read-only by default; write tools (`send_message`, `opt_in_contact`, `opt_out_contact`) require `NOTIFY_MCP_ENABLE_WRITES=true`. Bulk send is deliberately never exposed here.
- **A client business's own team logging in directly (not just their backend)** — the tenant portal at `/portal` (dashboard with stat cards + 14-day activity chart, Campaigns, Contacts, Templates, Inbox, Analytics), a fully parallel auth system to the admin console: `tenant_portal_users` table, `notify_tenant_session` cookie, `lib/tenantPortalAuth.ts`. Accounts are created by ops from the tenant page's Portal access tab — no self-serve signup, matching `admin_users`. Portal users never see Credentials, API keys, or any other tenant. See the "tenant portal" section below for the isolation details.
- **"What exactly did that campaign do?"** — the History button on every campaign row (admin and portal) opens `CampaignDetailSheet`: the exact message sent (from `notify_log.body_preview`), live per-recipient delivered/read/failed outcomes correlated via `meta->>'broadcastId'`, and every reply. Backed by `getCampaignDetail()` in `apps/admin/src/lib/campaigns.ts`.

`apps/api` runs via `ts-node` with no file watcher — after editing anything under `apps/api/src/lib/tenantRegistry.ts` (or any file it imports), the running dev process must be killed and restarted for the change to take effect; it will not hot-reload like `apps/admin`'s Next.js dev server does.

There is no working `lint` command — `turbo run lint` is wired up but no app defines a `lint` script and `packages/notify` references `eslint` without it being installed or configured. Don't invoke it as if it works.

Every app/package builds independently via `tsc`/`next build`; there's no cross-package type-checking shortcut beyond `pnpm --filter <name> exec tsc --noEmit`.

## Architecture

### `packages/notify` — tenant identity is bound at adapter-construction time, not threaded through calls

`NotifyClient` is the orchestrator (`send`, `sendBulk`, `syncTemplates`, `optIn`/`optOut`, webhook methods), composed of `TemplateEngine` (builds the Meta payload — checks `hsmTemplate` → `attachment` → built-in/custom template, in that priority order), `GuardEngine` (opt-in/quiet-hours/mute checks before every send), `EventBus`, an `IQueueAdapter` (`InlineQueueAdapter` runs synchronously; `BullQueueAdapter` is genuinely async via Redis), and an `IStorageAdapter` (`InMemoryAdapter` or `PostgresAdapter`).

Multi-tenancy is layered on **without changing any of the above**: `PostgresAdapter` takes an optional `tenantId` in its constructor and scopes every query to it (defaulting to a constant `LEGACY_TENANT_ID` if omitted, so old single-tenant callers keep working unchanged — never unscoped). `TenantClientRegistry` resolves and caches one full `NotifyClient` per tenant on demand, each with its own tenant-scoped `PostgresAdapter` and its own `WhatsAppHttpClient` (that tenant's access token baked in at construction). No method anywhere takes a `tenantId` parameter — the tenant is fixed for the lifetime of a cached client. `TenantWebhookRouter` extends this to inbound webhooks: it peeks `phone_number_id` out of the raw Meta payload (there's no tenant identifier otherwise), resolves the tenant, then verifies the signature against **that tenant's own** `appSecret` before dispatching — signature verification (`webhook/signature.ts`) fails closed (missing secret/signature → reject), which is a deliberate fix, not the original behavior.

Credential encryption (`security/CredentialCipher.ts`) derives a per-tenant AES-256-GCM key from one root key via HKDF rather than storing per-tenant keys — `MasterKeyRing`/`resolveKeyForVersion`/`reEncryptToCurrentVersion` support rotating the root key without a KMS. `security/PasswordHash.ts` (scrypt) is reused as-is for API key hashing, not just admin passwords — don't mistake it for password-specific.

`WebhookHandler.handleInboundMessage()` persists the reply (`storage.logReply()`), fires `onReply`/the event bus, and runs STOP/START **before** attempting to mark the inbound message as read on Meta's API. That ordering is deliberate, not incidental — the read-receipt call used to run first and, being a real network call to Meta, any failure there (expired token, rate limit, transient outage) silently discarded the reply and skipped STOP/START entirely. It's now try/caught and logged as non-fatal, last. Don't reorder this back without re-introducing that bug.

`NotifyClient.optIn()`/`optOut()` persist the consent change to storage first, then send a WhatsApp confirmation message wrapped in the same best-effort try/catch pattern as the read-receipt call — **deliberately non-fatal**. The confirmation is a session message, so Meta rejects it (error 131047) for any number outside the 24h customer-service window; before the guard was added, that exception (a) failed the admin Test Send for every fresh number (the route opts the number in first) and (b) propagated through `handleInboundMessage`, making the STOP/START webhook respond non-2xx and putting Meta into a retry loop. Don't "clean up" those try/catches — the consent write must always stick even when the courtesy message can't be delivered.

**`TenantClientRegistry`'s `onClientReady` hook is the extension point for any new feature that reacts to send/delivery/reply events** — every feature added after the initial scaffold (AI auto-reply, outbound webhooks, shared-inbox conversation tracking) is wired this way, and any future one should be too, rather than editing `WebhookHandler.ts` or `NotifyClient` itself:
```ts
new TenantClientRegistry({
  credentialsProvider,
  pool,
  onClientReady: (client, tenantId) => {
    client.eventBus.on('reply', (reply) => { /* ... */ });
    client.eventBus.on('sent' | 'delivered' | 'read' | 'failed', (event) => { /* ... */ });
  },
});
```
It fires once per built client (before caching), so listeners never need to guard against double-registration. Both `apps/admin` and `apps/api` have their own `tenantRegistry.ts` with their own `onClientReady` — **they are not wired identically, and that's deliberate**: real inbound WhatsApp webhooks land *only* on `apps/api`'s `/v1/webhook/whatsapp`, so anything reacting to `'reply'` (AI auto-reply, conversation upsert) is wired *only* in `apps/api/src/lib/tenantRegistry.ts` — wiring it in `apps/admin` too would just be dead code that never fires. Anything reacting to `'sent'/'delivered'/'read'/'failed'` (outbound event webhooks) needs wiring in **both**, since a send can originate from either app (Test Send/Campaigns in `apps/admin`, or a tenant's own `/v1/send` call). Every listener owns its own try/catch and never throws — a slow/failing side effect (an LLM call, a tenant's webhook endpoint being down) must never affect the webhook's response to Meta or a send's return value.

### `apps/admin` — Next 14 middleware can't run `node:crypto`

Session auth is deliberately split across two layers: `src/middleware.ts` runs on the Edge runtime and can only do a cheap cookie-*presence* check (Next 14's middleware has no Node runtime option, so it can't call `verifySessionToken`, which needs `node:crypto`). The actual authorization boundary is `src/lib/auth.ts`'s `requireAdminSessionOrRedirect()` (Server Components) and `withAdminSession()` (Route Handler wrapper), both of which run in the Node runtime and do real cryptographic verification. Every protected page/route calls one of these explicitly — the middleware is a UX nicety, not the security boundary. Don't "simplify" by moving verification into middleware; it will silently break.

Each tenant's admin screen (`src/app/tenants/[id]/`) is `TenantWorkspaceTabs.tsx`: a Workspace/Setup segmented toggle over two independent `Tabs` trees — Workspace (Analytics — default — / AI assistant / Portal access / Webhooks / Audit log) and Setup, a numbered onboarding pipeline (1 Branding → 2 Credentials → 3 Templates → 4 Test send → 5 API keys). One panel component per tab, each independently fetching and mutating via its own `/api/tenants/[id]/...` routes. `AnalyticsPanel` is the one panel that fetches client-side on mount rather than receiving server-rendered props, since it's meant to be refreshable without reloading the whole page. Campaigns (contacts, broadcast lists, HSM template sends against a list), Inbox (shared conversation view), and Contacts (tag management) each live on their own separate `/tenants/[id]/{campaigns,inbox,contacts}` page rather than as additional tabs — reserve the tab bar for per-tenant *configuration*, put anything that's really its own workspace on a separate page. Shared visual vocabulary lives in `components/`: `PageTitle` (page headers), `CardTitleGroup` (settings-card headers, icon chip + one-line description), `HelpSteps` (onboarding "where to find these keys" asides), `ActivityChart` (dependency-free SVG area chart, CSS-token colors so both themes work).

UI is shadcn/ui (`base-nova` style, **Base UI** primitives, not Radix — `render` prop instead of `asChild`) + Tailwind v4, dark mode by default. Gotchas worth knowing before touching UI code:

- Next 14.2 doesn't export `Geist` from `next/font/google` (needs Next 15) — the font stack is a plain system-ui fallback, not Geist.
- shadcn's generated `Input`/`Textarea` wrappers don't forward refs under React 18, so file-input "clear after upload" logic uses a `key`-based remount instead of `ref.value = ''`.
- A `'use client'` component that does a **runtime** (not `import type`) import of anything from a `src/lib/*.ts` module which itself imports `@orgname/notify` will transitively pull `BullQueueAdapter` → `bull` → Node's `child_process` into the client bundle, breaking the page with `Module not found: Can't resolve 'child_process'`. If a client component only needs a type or a small constant from such a module, use `import type` for the type and re-declare the constant locally rather than importing it at runtime (see `WebhooksPanel.tsx`'s inlined `ALL_WEBHOOK_EVENTS` for the pattern, matching `ApiKeysPanel.tsx`).
- Base UI `Tabs` cannot be trusted with `defaultValue` for any tree that isn't visible at first mount (multiple sibling lists, conditionally-mounted trees, or trees starting `display:none` — the initial tab silently never activates and never recovers). The only reliable pattern is a **fully controlled** `Tabs` (`value`/`onValueChange` with locally-owned state) and keeping all trees always mounted, toggling visibility with a CSS `hidden` class — see `TenantWorkspaceTabs.tsx`.
- Base UI `Select`'s `Select.Value` renders the **raw value** in the trigger (a UUID, `__all__`, …) unless the root gets an `items` map of value → label. Every `<Select>` with non-human-readable values must pass `items`.
- After a login `fetch` succeeds, navigate with `window.location.assign(...)`, not `router.push(...)` + `router.refresh()` — the push/refresh combo races when the target is a redirect-only page and strands the user on a blank tree that reads as a failed login (both `login/page.tsx` files carry the comment).

### `apps/admin` — the tenant portal is a parallel auth system, not a role on the admin one

`/portal/*` (tenant-facing) and the ops console share the `apps/admin` process but nothing else auth-wise: portal users live in `tenant_portal_users` (migration `018`), get a `notify_tenant_session` cookie, and are verified by `lib/tenantPortalAuth.ts` — whose AES-GCM key is **HKDF-derived from `SESSION_SECRET` with a portal-specific info string**, so a portal token can never decrypt as an admin token or vice versa (this closed a real cross-system session-replay hole; don't "simplify" both verifiers onto the raw secret). `middleware.ts` branches on `/portal*` paths to check the portal cookie; `getAdminSession()` additionally validates payload shape (`adminUserId` + known role) as defense in depth.

Portal pages reuse the admin panel components (`CampaignsPanel`, `ContactsPanel`, `InboxClient`, `AnalyticsPanel`, …) via an optional `baseApiPath` prop defaulting to the admin literal — portal pages pass `/api/portal`. Portal API routes (`app/api/portal/**`, all `withPortalSession`) never take a tenant id from the URL: the tenant comes from the verified session cookie only, so cross-tenant IDOR by URL-guessing is structurally impossible. Any resource id a portal route *does* accept in the body (e.g. `broadcastListId` on campaign create) must still be ownership-checked against `session.tenantId` (see `getBroadcastList` usage). Login normalizes email with `.trim().toLowerCase()` at every read/write site — an account created with a stray space was otherwise silently unable to log in.

### `apps/api` — two independent surfaces sharing one process

`/demo/*` (original) is a single hardcoded `NotifyClient` built from `WA_*` env vars, in-memory storage, no auth — a reference for the SDK's basic API shape. `/v1/*` (`src/routes/v1.ts`) is the real multi-tenant surface: `Authorization: Bearer <api key>` resolves a tenant via `lib/apiKeyAuth.ts` (hash lookup by key prefix, same `PasswordHash` primitive as admin logins), then routes through the same `TenantClientRegistry` pattern as `apps/admin`. The two surfaces don't share credentials or storage scope.

Webhook mounts (`notify.webhookExpress(app)` for `/demo`, the `v1Router`'s own webhook routes for `/v1`) are registered **before** the app-wide `express.json()` call in `index.ts`, not after. This is load-bearing: `body-parser`'s json middleware no-ops if the body was already parsed upstream, so a generic parser registered first would silently prevent the webhook route's own `express.json({ verify })` from ever capturing the raw body needed for HMAC signature verification. If you add a new route that needs the raw body, mount it before the generic parser too.

### Database

Migrations are additive and numbered (`001`–`019` in `packages/notify/src/adapters/storage/migrations/`); `001` is the original single-tenant schema (`notify_log`, `notify_preferences`) and is never edited, only extended by later files. `004` is the one genuinely structural migration — it swaps `notify_preferences`'s primary key from `phone` alone to `(tenant_id, phone)`, since the same phone number can be a different tenant's customer with independent consent state. New tenant-scoped tables always get a `tenant_id` FK and an index on `(tenant_id, ...)`. `011` adds `campaigns.broadcast_id`, a real column mirroring the `broadcastId` `BulkSender` already tags into every `notify_log.meta` row during a bulk send — added specifically so analytics queries don't have to reach into jsonb on every read.

`013`–`018` back the features in the "Real-world use cases" list above: `ai_configs` (+ `notify_preferences.ai_reply_count`/`ai_autoreply_disabled`/`ai_handoff_summary`, reusing the existing per-`(tenant_id, phone)` row as thread state rather than a separate table) and the atomic `claim_ai_reply_slot()` function; `webhook_endpoints`; `notify_log.body_preview` (populated by `extractBodyPreview()` for the WhatsApp-style message preview in Test Send/Campaigns and for MCP's `list_recent_logs`); `conversations`, with `UNIQUE(tenant_id, contact_phone)` **from creation** (a real race a similar open-source project hit in production — worth avoiding rather than discovering later); `contacts.tags` (`TEXT[]`, GIN-indexed); `018` adds `tenant_portal_users` (globally-unique email — login has no tenant selector) plus `campaigns.created_by_tenant_user_id`, so a campaign is attributed to whichever kind of user created it (`created_by_admin_id` stays for ops). `019` adds `tenants.category` and `tenant_wa_credentials.onboarding_method` (`'manual' | 'embedded_signup'`) for the Tech Provider roadmap (`docs/whatsapp-platform-roadmap.md`): category drives which starter templates (`apps/admin/src/lib/starterTemplates.ts`, submitted to Meta via `POST /{waba_id}/message_templates` in `metaGraph.ts`) a tenant sees first, and `onboarding_method` is a permanent fork, not a migration flag — the Embedded Signup path (shipped dormant: `lib/embeddedSignup.ts` + `EmbeddedSignupButton.tsx`, activated purely by env vars per `docs/phase2-launch-checklist.md` once Meta approves the platform app) and manual credential paste coexist forever, identical to everything downstream of credential storage. The Analytics tab/portal analytics also surface per-tenant sending health (`lib/sendingHealth.ts`): unique recipients in a rolling 24h from `notify_log` plus Meta's `quality_rating`/`messaging_limit_tier`, fetched best-effort with a 5s timeout so a Meta outage can never break the dashboard.

`apps/admin/scripts/seed-demo-data.sql` (run with `psql -f`) loads an idempotent demo dataset into the AZentis tenant — tagged contacts, a broadcast list, a completed + draft campaign, a week of `notify_log` rows across every status, replies, and conversations — purely for exercising the UI (analytics charts, campaign history, inbox) with realistic volumes. Fixed UUIDs + `ON CONFLICT DO NOTHING`, so re-running is a no-op.

### `packages/mcp-server` — a pure `/v1` API consumer, nothing more

Thin MCP (Model Context Protocol) server: `NotifyApiClient` wraps `apps/api`'s `/v1/*` routes with a normal `Authorization: Bearer <tenant API key>` header — no direct DB or SDK access, no special privileges, subject to the exact same rate limiting and `GuardEngine` opt-in checks any other `/v1` caller gets. `list_recent_logs` is always registered; `send_message`/`opt_in_contact`/`opt_out_contact` only register when `NOTIFY_MCP_ENABLE_WRITES=true` (default off) — an AI assistant shouldn't be able to send real messages or change consent state just because it's pointed at a tenant's key. `send-bulk` is deliberately never exposed here at all, in this package or `NotifyApiClient` — a single misfired tool call sending one message is a very different blast radius than one sending a broadcast, and an LLM-driven tool call is exactly the context where "are you sure?" doesn't get a chance to run.

If you touch `src/tools/write.ts`: import zod from the `zod/v3` subpath (`import { z } from 'zod/v3'`), not the barrel `zod` package. The MCP SDK's `registerTool` generic signature is defined against `zod-compat.d.ts`'s `AnySchema = z3.ZodTypeAny | z4.$ZodType` (using the `zod/v3`/`zod/v4/core` subpaths specifically); importing the barrel `zod` package instead (which, from 3.25.x on, is itself a hybrid v3/v4-core build) forces TypeScript into a deep structural comparison between two different type universes and blows up with `TS2589: Type instantiation is excessively deep and possibly infinite` on any multi-key `inputSchema`.

### Analytics — live-computed, never cached

`apps/admin/src/lib/analytics.ts` never trusts `campaigns.stats` (a write-once snapshot from the moment `sendBulk()` returned, before any delivery/read webhooks or replies could arrive) — it recomputes everything from `notify_log`/`message_replies` on every request. The per-campaign query uses two separate CTEs (send stats, reply stats) aggregated independently before a final join on `campaign_id`; joining `notify_log` and `message_replies` directly in one query would fan out and inflate the send counts by however many replies each message happened to get. If you touch this query, keep that separation.
